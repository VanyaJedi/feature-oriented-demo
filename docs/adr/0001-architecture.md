# ADR 0001: Feature-модули, hooks и явная сборка зависимостей

- Статус: принято для учебного демо
- Дата: 2026-09-08

## Контекст

Демо на React, TypeScript и Vite сопровождает статью о модульной архитектуре.
В нём три фичи: catalog предоставляет моковые товары, checkout собирает заказ,
delivery рассчитывает стоимость доставки. Цель — показать границы модулей и
замену зависимости на небольшом работающем примере.

В демо нет backend, роутера, SSR, React Query и Zustand. Не следует добавлять их
только ради соответствия полной архитектуре из статьи. DI-контейнер реализован
локально в `src/infrastructure/di/container.ts` и хранит готовые экземпляры.

## Решение

### 1. Слои и направления импортов

```text
app → pages → features → infrastructure → shared
```

Слой может импортировать свой слой и любой нижележащий, но не вышележащий.

- `app` собирает приложение и выбирает реализации зависимостей.
- `pages` компонует UI и hooks нескольких фич на экране.
- `features` владеют бизнес-правилами, операциями и интерфейсом своей области.
- `infrastructure` содержит общие технические механизмы, в демо — DI-контейнер.
- `shared` содержит общие компоненты, чистые утилиты и платформенные адаптеры.

Между разными фичами разрешены только type-only импорты и реэкспорты.
Runtime-вызов другой фичи выполняется через зависимость, переданную сервису
при сборке. Импорты токенов соседней фичи тоже являются runtime-импортами и
не служат исключением из этого правила.

Между разными страницами импорты запрещены. Модули infrastructure и shared могут
использовать соседние модули своего слоя; циклы не допускаются.

`src/main.tsx` — точка запуска: регистрирует сервисы и монтирует React-приложение.
Бизнес-правила в ней не размещаются.

### 2. Каталоги внутри фичи

Создавайте только те каталоги, которые нужны задаче:

| Каталог | Ответственность |
| --- | --- |
| `di` | Токены и явные функции регистрации |
| `services` | Бизнес-операции и интеграции |
| `hooks` | Вызов сервисов, состояние и обработка действий в React |
| `model` | Типы, контракты, данные примера, схемы и мапперы при необходимости |
| `ui` | Компоненты фичи |
| `store` | Общее клиентское состояние, если появится потребность |
| `utils` | Чистые вспомогательные функции |

Сервисы не зависят от React, не управляют UI-состоянием и не обращаются к
контейнеру. Зависимости сервиса видны в конструкторе. Hooks получают собственные
сервисы через DI и связывают их с интерфейсом. UI передаёт пользовательские
действия в hooks. Для технического доступа к контейнеру hooks могут использовать
`@infra/di`; бизнес-операции остаются в сервисах своей фичи.

Небольшой чистый расчёт может оставаться обычной функцией. Не добавляйте сервис,
интерфейс или слой без конкретной необходимости.

### 3. Состояние

В текущем демо `useCatalog` загружает моковые товары в локальный `useState`,
а `useCheckout` хранит выбранные товары и вычисляет итог через сервис.
Это упрощение для примера, а не реализация кэша серверных данных.

Если появятся реальные запросы с кэшированием и инвалидацией, отдельно выбирается
инструмент серверного состояния, например React Query. Не дублируйте такой кэш
в клиентском store. Общий store нужен только для состояния, которое действительно
должны разделять несколько потребителей; локальное состояние остаётся в hook
или компоненте. Store не выполняет HTTP-запросы.

### 4. DI и запуск

- `createToken<T>(name)` создаёт уникальный типизированный токен.
- `register(token, instance)` сохраняет готовый экземпляр, повторный вызов заменяет его.
- `get(token)` возвращает экземпляр или выбрасывает ошибку для неизвестного токена.
- Контейнер не создаёт сервисы автоматически, не анализирует имена параметров,
  не поддерживает lazy-загрузку, scopes и освобождение ресурсов.
- Feature-функции `register...()` принимают `Container` аргументом и экспортируются
  из `di/index.ts`. Импорт модуля сам по себе не регистрирует сервисы.
- `registerApplicationServices()` в `src/app/di/registerServices.ts` использует
  общий `diContainer`, выбирает реализации и вызывает регистрации фич.
- `src/main.tsx` вызывает эту функцию до рендера React.

Класс `DeliveryPriceService` принадлежит delivery. Checkout импортирует
только тип класса через публичный вход `@features/delivery/services` и объявляет
токен своей зависимости с этим типом. App регистрирует
`DeliveryPriceService` под токеном, после чего функция регистрации checkout
передаёт готовую зависимость в конструктор `CheckoutService`.

Порядок регистрации важен: зависимость должна существовать до создания её
потребителя. Замена экземпляра в контейнере не обновляет зависимости уже созданных
сервисов; для другой конфигурации нужно заново собрать потребителей.

Для единственной реализации можно использовать тип класса. Когда появляется
несколько реализаций и требуется отдельный контракт, выделяйте небольшой интерфейс
в delivery. В этом демо используется непосредственно тип класса без отдельного интерфейса.

Общий экземпляр контейнера подходит текущему клиентскому демо. Если появится SSR,
зависимости с пользовательскими данными потребуется изолировать на запрос.

### 5. Публичные входы и имена

Алиасы объявлены в `tsconfig.app.json` и `vite.config.ts`:

- `@app/*` → `src/app/*`
- `@pages/*` → `src/pages/*`
- `@features/*` → `src/features/*`
- `@infra/*` → `src/infrastructure/*`
- `@shared/*` → `src/shared/*`

Внешний код использует публичные входы каталогов фичи, например
`@features/catalog/model`, `@features/checkout/di`, `@features/catalog/ui`.
Корневой barrel `@features/catalog` запрещён. `index.ts` нужен у каталога,
который предоставляет публичный API; пустые файлы для структуры не создаются.
Внутри каталога разрешены относительные импорты, между каталогами одной фичи
используйте их публичные входы, например `../model`.

- Сервис: `*.service.ts`, класс `*Service`.
- Hook: `use*.ts`, функция `use*`.
- Компонент: `PascalCase.tsx`.
- DI-токены: `di/tokens.ts`, имя `*Token`.
- Модель: `*.types.ts`, при необходимости `*.schema.ts`, `*.mapper.ts`.
- Моковые данные: `*.mock.ts`.

### 6. Платформенные API

Браузерные API читаются через `@shared/platform`. В адаптерах используйте
`globalThis` и проверку доступности. Сейчас реализован `getBrowserDocument()`;
другие accessors добавляются только по необходимости.

Переиспользуемые модули не читают DOM или storage при импорте. Их сервисы также
не должны запускать браузерные побочные эффекты из конструктора. Платформенная
точка запуска `src/main.tsx` может получить корневой DOM-элемент и завершиться
понятной ошибкой, если приложение запущено без браузерного root.

Учитывайте отсутствие API: возвращайте `null`, пропускайте необязательную
операцию или выдавайте понятную ошибку для обязательной. При работе со storage
проверяйте не только наличие объекта, но и ошибки чтения/записи. Hooks и UI
остаются связанными с React; это не мешает независимо проверять сервисы.

### 7. Автоматические проверки

```bash
npm run lint
npm run test:lint
npm run typecheck
npm run build
```

ESLint проверяет направление слоёв, runtime cross-импорты фич, импорты между
страницами, корневые входы фич и прямой доступ к браузерным API. Правило работает
с алиасами демо, относительными путями, реэкспортами и строковыми динамическими
импортами. Исполняемые примеры находятся в `eslint/architecture.test.js`.

Проверка не доказывает отсутствие циклов, не проверяет каждый публичный вход,
вычисляемые импорты, произвольные алиасы globalThis, защиту внутри адаптеров или
порядок регистрации DI. Эти свойства проверяются при ревью и подходящими тестами.

## Последствия и альтернативы

Границы фич и параметры конструкторов показывают зависимости. Сервис можно
проверить без React, передав тестовую реализацию. Цена — дополнительные токены,
регистрации и необходимость соблюдать порядок создания сервисов.

Для такого маленького приложения достаточно и ручной передачи зависимостей без
контейнера. Контейнер оставлен для иллюстрации статьи. Регистрация через побочные
эффекты импортов не используется, чтобы порядок сборки оставался виден.

Пересмотрите ADR при добавлении backend, роутинга, SSR, другого управления
состоянием или DI, а также если границы фич заставляют постоянно менять их вместе.
